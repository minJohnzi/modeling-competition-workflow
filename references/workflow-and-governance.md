# Workflow and Governance

本参考定义一次数学建模竞赛任务从发现到交付的控制流程。竞赛官方要求、项目仓库规则和用户明确授权优先于本文。

## 1. Determine the current phase

### DISCOVER

只读检查竞赛官方题目、附件数据、模板要求、现有代码、已有结果、论文草稿、运行日志和仓库规则。输出至少包括：

- 赛制 Profile（国赛 / 华为杯 / 美赛 / 邀请赛）与对应硬约束（页数、语言、匿名、官方表）；
- 问题理解、子任务拆分与各问核心题型识别（机理仿真 / 运筹优化 / 统计预测 / 评价决策）；
- 当前实现、结果和状态；
- 数据质量与口径发现；
- 主要矛盾、风险和冲突；
- 待确认假设与验收标准草案。

此阶段不能生成正式模型结论，也不能把参考答案数字转写为项目结果。

### DESIGN

提出推荐方案和至少一个合理备选。若确实没有备选，说明排除原因。每个方案说明：

- 研究目标与所属题型；
- 输入与输出（含是否需要输出官方指定结果表）；
- 核心数学模型与算法设计；
- 假设与约束（物理/数学边界、单位制、时空粒度）；
- 简单基线和合理竞争方法；
- 题型专属验证、敏感性与边界设计；
- 拟修改文件和预期产物；
- 计算成本、时间预算与升级停止条件。

以实施契约结束，明确授权范围、验收标准和仍需用户裁决的事项。

### AWAIT_APPROVAL

只在项目或用户要求批准门槛时等待。批准必须能映射到一个明确方案和文件范围。模糊批准不扩张权限。

### EXECUTE

在批准范围内完成代码、正式结果、官方结果表、图表、运行日志和论文草稿。执行中持续维护证据链，不把写作留到模型全部结束以后。

### VERIFY

验证不只运行单元测试，还要针对题型独立重算关键物理量、守恒残差、硬约束覆盖、泛化切分、权重稳定性、统计口径和结论数字。证据不足的结果标为待验证。

### INTEGRATE

多问题项目完成接口契约、符号表、图号表号、术语、时空范围、误差传递和结论强度的统一。检查上游变更是否已传播到所有依赖产物，并按赛制要求完成匿名审查与版面/页数控制。

### CLOSE

交付结果、复现命令、验证证据、审计输出、局限和未完成事项。不要用“完成”掩盖仍待审核或只通过局部验证的状态。

## 2. Separate permissions from technical confidence

授权状态和结论可信度是两条不同轴：

| 维度 | 典型状态 | 含义 |
|---|---|---|
| 工作授权 | DISCOVER / APPROVED / EXECUTING | 是否允许写入或运行正式流程 |
| 结论状态 | PROVISIONAL / SUPPORTED / INVALID / STALE | 当前证据是否支持进入论文与官方结果表 |

“已批准实施”不等于“结果已验证”；“测试通过”也不等于“已获准覆盖正式产物”。

## 3. Freeze decisions that affect downstream work

对以下内容维护锁定决策（建议写入 `PROJECT_STATE.md`）：

- 官方字段语义、单位制、坐标系与数据源；
- 时间/空间索引、边界条件、步长或离散粒度；
- 样本 Scope、分母与聚合方法；
- 跨问题传递内容、数值精度与误差界；
- 核心目标函数、软惩罚权重与评价指标定义；
- 正式主场景、基准方案与压力情景的关系；
- 官方提交模板（如 `result*.xlsx` 格式、页数上限、匿名规则）。

每条决策记录编号、原因、影响范围、状态和证据。变更后显式标记受影响产物为 `STALE`。

## 4. Reapproval triggers

以下变化通常属于重大变更：

- 重新解释题意、官方字段或官方填表口径；
- 改变数据剔除、填补、聚合或异常处理；
- 更换主模型、目标函数、控制方程或关键约束；
- 改变核心参数范围、主场景、评价权重或基线；
- 将一个子问题的数值结果或代理模型作为另一个子问题的新输入；
- 改变结论方向或最优性表述；
- 跨越已批准目录写入。

格式修复、运行失败修复、日志补充和不改变模型含义的重构可在原范围内处理，但交付时说明。

## 5. Time-budgeted competition execution

在竞赛时间约束下（如国赛/美赛 72–96 小时、华为杯 96–108 小时）优先保证：

1. 官方口径与提交表结构正确；
2. 主流程端到端可运行；
3. 硬约束可行 / 物理守恒与数据无泄漏成立；
4. 简单基线与主模型同口径可比较；
5. 正式数字、表格与论文可追溯且一致；
6. 核心论文段落与匿名/页数门槛完整达标。

只有前述门槛通过后，才增加更多对比模型、复杂可视化、参数网格或装饰性工作。达到预设时间上限时停止新实验，立即完成验证、归档和论文闭环。

## 6. Handoff contract

跨成员、跨 Agent 或跨问题交接至少写明：

- 当前事实源及其版本或 SHA-256 哈希；
- 已锁定和未确认的口径；
- 允许继承的定义、方程、算法和字段；
- 禁止继承的固定排程、旧数字和失效假设；
- 上游参数的拟合误差或不确定性区间；
- 当前正式产物及状态；
- 复现命令和测试结果；
- 下游必须重新计算的内容。

## 7. Parallel worker & subagent ownership boundaries

多子问题（如 `q1`–`q5`）或多角色（建模、绘图、论文）采用多 Agent 或多 Git worktree 并行推进时，强制遵守以下写入隔离规则：

1. **子问题 Worker 独占边界**：负责 `qN` 的 Worker 只允许写入 `qN/` 目录内的文件；不得直接修改其他子问题的 `qM/` 目录。
2. **共享与上游只读原则**：对上游 `qM/outputs/`、`shared/`（如公共数据预处理、公共绘图风格）以及根目录治理文件（`PROJECT_STATE.md`、`INTERFACE_CONTRACTS.md`、`ARTIFACT_REGISTRY.md`），子问题 Worker 默认**只读**。若需修改公共模块或上游接口，必须向主协调者（Coordinator）提交变更请求，不得擅自覆写。
3. **Coordinator 统一集成**：根目录状态登记、跨问题接口冻结、全局符号表合并、总论文整合及最终匿名打包，统一由 Coordinator 在 `INTEGRATE` 与 `CLOSE` 阶段写入和签发。
4. **防产物污染**：各分支/Worktree 的临时缓存（`.pytest_cache/`、`__pycache__/`、`tmp/`）严禁合入正式输出目录 `outputs/`。
